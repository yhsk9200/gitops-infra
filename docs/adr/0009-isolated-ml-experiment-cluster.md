# ADR-0009: 격리 ML/LLMOps 실험 클러스터 — 프로덕션·실험 플레인 분리

## 상태

승인됨

## 날짜

2026-07-16

## 맥락

ADR-0008이 MLOps 방향(MLflow 공용 서비스 + 제품 테넌트)을 확정했지만 그 설계는 12GB 확정 예산 안의 **경량 파이프라인**(수 MB 모델, CPU 학습)을 전제한다. "더 큰 ML/LLM 인프라를 직접 굴려보는 학습"은 그 예산 안에 들어가지 않는다.

한편 운영자가 보유한 Mac(Apple M5 Pro, 18코어/48GB RAM, arm64, 디스크 여유 629GB)이 인프라 판단에 반영돼 있지 않았다 — ADR-0008에서 NAS(DS920+)를 뒤늦게 반영했던 것과 같은 종류의 누락. 2026-07-16 환경 실측:

- Mac은 **이미 tailnet에 편입**돼 있음(`100.114.123.60`). OCI 노드·NAS 편입(ADR-0008 Phase A)만 남음.
- Mac → OCI 노드 TCP 왕복 ~13ms — WAN 클러스터 연동에 충분.
- OrbStack 2.2.1 가동 중 — 다중 Linux VM(arm64, systemd) 생성 가능. OCI 노드와 아키텍처 동일.
- **제약 실측: macOS 위 Linux VM에는 Metal GPU 패스스루가 존재하지 않음** — VM/k8s 경로의 워크로드는 CPU 전용. Apple GPU를 쓰는 추론/학습은 macOS 네이티브(Ollama/MLX/PyTorch MPS)만 가능.

## 검토한 대안

### Mac 자원의 편입 방식

| 대안 | 기각/채택 사유 |
|---|---|
| OCI 클러스터에 Mac을 agent 노드로 조인 (k3s agent in VM + tailnet) | 기술적으로 가능하나: ① 노트북의 sleep/이동/재부팅이 **프로덕션 클러스터의 NodeNotReady 이벤트로 유입** — taint/toleration 설계로 완화해도 결합 자체는 남음 ② local-path PVC가 노드 종속이라 스케줄 가능한 워크로드가 무상태 잡으로 한정 ③ 실험용 CRD(Kubeflow, KServe 등)를 prod 클러스터에 설치하게 됨 — blast radius가 실험 목적과 상충 ④ 멀티노드 스케줄링 학습 불가(agent 1개 추가일 뿐) |
| Mac 자원을 클러스터 없이 사용 (네이티브 학습만) | GPU 학습엔 유효하나 "ML 인프라를 직접 굴리는 학습"(스케줄링, 오케스트레이션, 서빙 스택)이 목적에서 빠짐 |
| **격리 클러스터 + 최소 연결 (채택)** | Mac에 독립 k3s 클러스터(OrbStack VM 1~3노드). 프로덕션 리스크 0(꺼져도 OCI는 모름), CRD·버전 자유, 멀티노드 토폴로지 학습 가능, 12GB 예산 불침범. 실조직의 "프로덕션 플레인 vs 실험 플레인" 경계 재현 |

### 관측 연결 방식

| 대안 | 기각/채택 사유 |
|---|---|
| Mac 클러스터 metrics를 OCI Prometheus로 remote_write / 전량 federation | OCI Prometheus는 ADR-0004로 1Gi limit·5d retention — 두 번째 클러스터 전량 유입은 리핏 예산 파괴 |
| **OCI Grafana에 Mac Prometheus를 두 번째 datasource로 추가, tailnet 경유 (채택)** | OCI 측 저장 비용 0. 대시보드 한 화면에 두 클러스터. Mac이 꺼지면 해당 패널만 no data — 간헐 가동 전제와 일치 |
| Mac 클러스터 가용성 알림 (down → Telegram) | 노트북의 꺼짐은 정상 상태 — "정상인 꺼짐"에 알림을 달면 노이즈(PR #28의 InfoInhibitor 교훈 재발). 알림은 가동 중 이벤트(잡 실패 등)로 한정하되 그것도 실수요 등장 시 |

### GitOps 경계

| 대안 | 기각/채택 사유 |
|---|---|
| OCI ArgoCD가 Mac 클러스터를 원격 클러스터로 관리 | 컨트롤 플레인 결합 — Mac이 꺼질 때마다 프로덕션 ArgoCD에 sync 실패 누적, "격리" 전제 붕괴. prod ArgoCD에 실험 클러스터 자격증명이 들어가는 것도 노출 표면 증가 |
| 이 레포(gitops-infra)에 Mac 클러스터 매니페스트 동거 | 수명주기가 다름 — Mac 클러스터는 수시 파괴·재구축이 전제인 실험장. ADR-0005 "경계는 수명주기·소유권 단위" 원칙 위반 |
| **자체 컨트롤 플레인 + 별도 레포 (채택)** | Mac 클러스터는 자기 GitOps(도구는 미해결 — 아래)와 자기 레포를 가짐. 두 클러스터는 서로의 컨트롤 플레인을 모름 |

### MLflow(기록의 원본) 배치

| 대안 | 기각/채택 사유 |
|---|---|
| MLflow를 Mac 클러스터로 이동 | 모델 레지스트리(durable state)가 노트북 가용성·백업에 묶임. ADR-0008 백업 확장 설계도 무효화 |
| **OCI 유지 — ADR-0008 무수정 승계 (채택)** | durable 상태는 24/7 클러스터, 컴퓨트는 Mac. Mac 클러스터의 학습/실험 잡은 tailnet 경유 **MLflow 클라이언트**로 기록 |

## 결정

1. **Mac에 완전 격리 k3s 클러스터를 구축한다** — OrbStack Linux VM 기반, arm64, 멀티노드 토폴로지(server 1 + agent 1~2) 허용. 프로덕션(OCI)과 동일 클러스터가 아니며 노드 조인도 하지 않는다.
2. **연결 계약 — 아래 세 지점만 허용, 나머지는 기본 거부:**
   - **전송로**: tailnet. 클러스터 간 서비스 노출은 명시적으로 선택한 Service만(Tailscale operator 또는 동등 수단).
   - **관측**: OCI Grafana ← Mac Prometheus datasource (읽기 단방향).
   - **기록**: Mac 클러스터 워크로드 → OCI MLflow 클라이언트 기록 (ADR-0008 proxied artifacts 경로 그대로).
3. **비연결 명시**: OCI ArgoCD의 Mac 클러스터 관리 금지 · Mac 클러스터 가용성 알림 금지 · 클러스터 간 워크로드 스케줄링 금지 · OCI 쪽 어떤 컴포넌트도 Mac 클러스터 가용성에 의존하지 않는다(의존 방향은 항상 Mac→OCI 단방향).
4. **GPU 워크로드는 k8s 밖**: Metal GPU가 필요한 추론/학습은 macOS 호스트 네이티브(Ollama/MLX/MPS)로 실행하고, Mac 클러스터의 파드(게이트웨이·RAG·eval·오케스트레이션 — 전부 CPU 스택)가 호스트 엔드포인트를 호출하는 하이브리드로 간다. "VM에 GPU가 안 온다"는 제약을 설계로 수용.
5. **별도 레포** (이름 미정): Mac 클러스터의 부트스트랩·매니페스트·문서는 이 레포 밖. 이 레포에는 본 ADR과 연결 계약의 OCI 측 반영(Grafana datasource 등)만 남는다.
6. **ADR 관계**: ADR-0002(단일 노드)·ADR-0008(MLOps)은 무수정 유지 — OCI 클러스터는 계속 단일 노드이고, MLflow·승격·서빙 경로는 그대로다. 본 ADR은 그 옆에 실험 플레인을 추가할 뿐이다.
7. **자원 상한**: VM 총 할당 상한 24GB/12코어 이내(호스트 여유 실측 기반) — Mac의 일상 사용을 침범하지 않는 선.

## 근거

- **blast radius 0**: 실험(임의 CRD, aggressive 업그레이드, 파괴·재구축)이 프로덕션 클러스터·12GB 예산·알림 라인에 어떤 경로로도 닿지 않는다. 연결 계약 세 지점이 전부 Mac→OCI 단방향 의존이라 Mac 소멸 = 아무 일도 없음.
- **학습 범위 확장**: 단일 노드 OCI에서 원천 불가능한 멀티노드 스케줄링·drain·affinity와, 예산상 기각했던 오케스트레이터(Kubeflow/Argo WF)·서빙 스택(KServe/vLLM CPU)을 실험 플레인에서 자유롭게 다룬다.
- **기존 결정과의 정합**: "소비자 없는 컴포넌트를 prod에 들이지 않는다"(ADR-0003/0006/0007/0008)를 유지하면서 실험 수요는 격리된 플레인으로 흡수 — 절제 원칙과 학습 욕구의 충돌을 경계 분리로 해소.
- **실조직 패턴 재현**: 프로덕션 플랫폼 vs ML 실험 환경의 분리, 그리고 "연결은 관측과 기록뿐"이라는 계약은 실무의 멀티클러스터 경계 설계와 같은 구도다.

## 비목표 / 미해결

- Mac 클러스터 내부 GitOps 도구(자체 ArgoCD vs Flux vs plain 매니페스트) — 실험 레포 첫 결정 사항
- VM 토폴로지 상세(1노드 vs 3노드, 노드별 자원 배분) 및 실험 레포 이름
- Tailscale operator ACL 설계, 호스트 네이티브 추론의 서빙 계약(엔드포인트·모델 관리)
- Mac 클러스터에서 만든 모델의 프로덕션 승격 — 필요해지면 ADR-0008 이미지 베이킹 경로를 그대로 탄다(레지스트리는 동일 GHCR). 그 전까지 Mac 클러스터 산출물은 실험 기록으로만 취급

## 단계

- **Phase 0 (선행, ADR-0008 Phase A와 공유)**: OCI 노드 tailnet 편입 — 관측·기록 연결의 전송로. NAS 편입도 동일 작업에서.
- **Phase 1**: OrbStack VM + k3s 부트스트랩(실험 레포 생성), Mac Prometheus 기동.
- **Phase 2**: 연결 계약 이행 — OCI Grafana datasource 추가(이 레포 PR), MLflow 클라이언트 기록 실측.
- **Phase 3**: ML/LLM 스택 실험 — 오케스트레이터, 게이트웨이/RAG/eval, 호스트 네이티브 추론 하이브리드.

## 재검토 조건

- Mac 클러스터의 실험 워크로드가 **상시 서비스**로 승격 필요해지면 — OCI로 이전(테넌트 온보딩) 또는 노출 방식 재검토. 실험 플레인에 상시 소비자를 두지 않는다.
- GPU 워크로드가 k8s 스케줄링을 실수요로 요구하면(호스트 네이티브 하이브리드로 부족) — Linux GPU 머신/클라우드 GPU 재평가.
- 연결 지점을 세 개 넘게 늘리고 싶어지면 — 그 시점에 본 ADR 개정. 계약의 침식은 개정 없이 허용하지 않는다.
